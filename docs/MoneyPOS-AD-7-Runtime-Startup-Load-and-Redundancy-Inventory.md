# MoneyPOS AD-7：运行时启动负担与无效能力盘点/裁剪设计

## 结论

> **2026-09-22 用户决策：冻结启动优化。** 已知 Windows 打包版在 i7-8700 上重复启动约 15 秒；用户决定当前接受该表现，不继续进行 ENV-1 分段测量、HOME 延后刷新、Electron 健康检查调整或任何“裁剪以提速”实施。本文件保留历史盘点和测量协议，仅供未来用户明确重新授权时参考，不构成当前待办或推荐顺序。

本任务完成的是盘点和裁剪设计，**不删除源码、不关闭 Bean、不改启动参数或业务配置**。当前没有证据支持
“启动慢主要来自大量死代码”或直接批量移除依赖。桌面版可感知启动由 Electron 等待后端健康检查决定，后端又
分为嵌入式 MariaDB 前置启动和 Spring Boot 装配两段；必须先分段测量，才能把启动时间归因到某个能力。

当前应保留 MariaDB、Flyway、安全、多租户、文件存储、WebSocket、备份和支付字典校验。唯一可能显著占用
启动后数据库资源的业务动作是 HOME 日快照补偿/刷新；但它保障首页读模型和当天经营数据，属于“待测量的
延后执行候选”，不是无效代码。邮件、本地缓存、时区切面和 Swagger 的静态消费者较少或为零，是后续可验证的
小候选，但预期节省远小于数据库/进程启动，不能承诺提速。

## 范围与证据方法

- 只读检查 `money-app-biz` 启动入口、配置、自动配置、主动任务、前端 Electron 启动器和前后端消费者。
- “无效”须同时满足：没有生产调用者、没有 HTTP/WebSocket/定时/硬件/运维入口、没有条件装配依赖，并在
  隔离回归中证明移除后行为不变。仅“没有注入点”或“前端暂未出现菜单”都不足以删除。
- “启动负担”分为嵌入式数据库前置阶段、Spring 上下文、健康检查可达、Electron 窗口展示和应用就绪后的
  主动任务；不把请求期或每日定时任务误报为冷启动耗时。

## 当前启动路径

1. Electron `money-pos-web/main.cjs` 启动 Java JAR，并传入 `--app.home`。
2. `QkMoneyApplication` 因该参数调用运行时工作区；Windows 包装模式由
   `EmbeddedMariaDbGuardian` 初始化/复用 `mysqld.exe`、注入 `9102/money_pos` 数据源。
3. Spring Boot 组装数据源、Flyway、MyBatis、Web、安全、多租户、文件映射及业务 Bean。
4. `PaymentDictCheckRunner` 查询一次支付字典；缺失时拒绝启动。
5. `ApplicationReadyEvent` 触发 HOME 七日缺失补偿及当天快照刷新；同一能力之后每五分钟刷新一次。
6. Electron 轮询 `/money-pos/actuator/health`；失败后固定等待 1.5 秒再试，HTTP 200 后才创建收银窗口。

步骤 2 和 3/4 是首要冷启动测量段。步骤 5 的监听器会执行跨 TRADE/GMS/UMS 的汇总查询和 HOME 写入，须单独
记录，不得假定它等同于“健康接口可达之前”的阻塞。步骤 6 的固定轮询会给窗口展示引入最多约 1.5 秒的额外
等待粒度；它是可优化候选，不是无效功能。

| 能力 | 生产证据 | 分类 | 后续处理前提 |

| Electron 健康检查轮询 | 后端 200 后才创建窗口；失败路径固定 1.5 秒重试 | 待优化候选，不是死代码 | 对比轮询间隔/事件驱动方案的窗口可见时间、端口冲突与后端失败提示；Electron 改动须独立授权。 |

## 可重复测量协议

实际数字只能在 Windows 打包目录、真实 JRE、随包 MariaDB 和代表性历史数据下采集；该环境是 ENV-1，当前
未在本任务中伪造结果。后续测量至少记录 5 次“已有数据目录”启动和 1 次“首次初始化”，同一机器、同一安装
目录、同一数据副本下分别报告中位数和最大值。

| 时间点 | 定义 | 采集方式 |
| --- | --- | --- |
| T0 | Electron 调用 `spawn(java -jar ...)` | Electron 进程记录单调时间。 |
| T1 | 嵌入式 MariaDB 可连接 | 守护者现有启动日志或未来最小计时点。 |
| T2 | Spring Web 服务器可接受连接 | Spring 启动日志/端口探针。 |
| T3 | `/actuator/health` 首次 HTTP 200 | Electron 记录首次成功健康检查。 |
| T4 | HOME 启动快照完成或失败保留旧值 | `HomeDailySnapshotRefreshTask` 成功/失败日志带耗时。 |
| T5 | 主收银窗口 `ready-to-show` | Electron 窗口事件记录。 |

对比时使用 `T1-T0`（数据库）、`T3-T1`（Spring/Flyway/Runner）、`T5-T3`（桌面等待）和 `T4-T3`
（健康可达后的首页快照）四段，不以总时间猜测原因。任何候选只有在降低相应分段且不损失验收行为时才有实施价值。

## 若未来重新授权时的实施门槛与顺序

1. 先完成 AD-5 设计并在获准后实施 CI 门禁，保证删除/条件化改动有回归安全网。
2. 以本设计的 Windows 协议完成实际基线；若数据库阶段主导，优先优化 MariaDB 启动或 Electron 等待，不从低收益 Bean 开始。
3. 仅对一个已验证候选另立最小实施任务：优先评估 HOME 延后刷新或 Electron 健康检查等待；邮件/缓存/时区/Swagger
   只能作为独立、低风险的小切片。
4. 每个实施切片必须具备对应的特征/集成回归、冷/热启动对比和回滚点；不得混合数据库迁移、Maven 拆分或业务规则修改。

## 本任务验证与残余风险

- 已完成：启动入口、配置、主动任务、自动配置、后端消费者和 Electron/前端消费者的静态盘点；
  `scripts/architecture-scan.sh --check-new` 与 `git diff --check` 适用于文档收口。
- 未执行全量 Maven 测试或 Windows 启动：本任务未改生产/测试源码；Windows 实测属于 ENV-1，且直接启动开发库会触发
  HOME 写入，不应为盘点任务擅自执行。
- 残余风险：静态检索不能发现反射、外部运维脚本或用户手工访问 Swagger 的需求；因此所有“待裁剪验证”项仍不是删除授权。
