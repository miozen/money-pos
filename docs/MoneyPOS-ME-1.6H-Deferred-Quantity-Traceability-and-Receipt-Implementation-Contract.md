# MoneyPOS ME-1.6H：商品寄存与提货可追溯性、小票实施合同

> 状态：**Frozen implementation contract — approved to implement**；冻结日期：2026-10-10；适用分支：`dev`。
>
> 本合同承接已完成的 ME-1.6G，只处理 QUANTITY 商品寄存/提货的订单请求号一致性、业务显示名称和
> 小票能力，以及最终 Windows 验收。它不改变收入确认、库存扣减时点、支付、退款、既有订单结构或权限边界。

## 1. 已确认事实与目标

### 1.1 请求号事实

普通 POS 在 `usePosStore.prepareCheckout()` 中使用 `REQ${Date.now()}`。`Date.now()` 返回浏览器所在机器
系统时钟的 Unix epoch **毫秒数**；它不是按时区格式化的“本地时间字符串”。同一时刻在任何时区的 epoch 数值相同，
而本机时钟是否正确仍由操作系统保证。

当前 QUANTITY 寄存使用 `MB-QUANTITY-BUY-${Date.now().toString(36)}-*`，是为避免超过
`oms_order.order_no varchar(32)` 而引入的临时缩短格式。它已避免插入失败，但与普通订单视觉和运营习惯不一致。

### 1.2 提货事实

QUANTITY 提货不是普通销售订单。一次成功提货会同时写入：提货业务单和明细、会员数量权益扣减、以及
`MEMBER_PICKUP` 库存单/流水。`MEMBER_PICKUP` 是内部库存动作码，不能仅为显示名称而重写历史数据或跨域契约。

### 1.3 小票事实

寄存创建 `OmsOrder`，但当前提交成功后未调用普通结算已存在的
`POST /oms-order/hardware/checkout-receipt`。提货没有 `OmsOrder`，也没有提货专属小票接口或模板。

### 1.4 本阶段目标

1. 寄存订单请求号采用与普通 POS 相同的 `REQ` + epoch 毫秒格式；
2. 对操作员展示“会员提货”，保留 `MEMBER_PICKUP` 作为内部码；
3. 寄存成功自动打印普通订单小票；
4. 提货成功自动打印独立的“会员提货单”；
5. 在 Windows Electron 环境完成现有 ME-1.6F/ME-1.6H 的人工冒烟证据。

## 2. 冻结业务规则

- 寄存 `reqId` 固定为 `REQ${Date.now()}`，与普通购物车相同；13 位 epoch 毫秒加 `REQ` 共 16 字符，满足
  `oms_order.order_no varchar(32)`。它仍是幂等请求键而非面向顾客的订单号。
- 同一寄存提交重试必须复用首次生成的 `reqId`；仅在成功、取消/关闭或明确重新发起新交易时生成新的值。
- 提货的 `MP*` 提货单号仍是提货业务追溯号，`request_no` 仍是幂等键；本阶段不把提货伪装为普通订单，
  也不要求 `MP*` 改成 `REQ*`。
- 业务显示统一使用“会员提货”（允许页面简称“提货”）；内部数据库值、库存命令语义、历史审计和
  `MEMBER_PICKUP` 不变。
- 寄存小票复用普通订单结账小票：沿用现有订单号、订单明细、支付、开钱箱和失败提示规则。打印失败不得回滚已
  成功提交的寄存订单。
- 提货小票是非销售凭证：必须明确标题“会员提货单”，不得显示为销售订单、不得确认收入或生成支付记录。
  小票最少包含提货单号、会员业务识别信息、商品名称/数量、操作员、办理时间和“本次提货不产生销售收入”说明。
  打印失败不得回滚已完成的提货、权益扣减或库存扣减。
- 两类打印均只在成功响应后触发一次；页面重绘、查询和失败重试不得隐式重复打印。补打入口不在本合同范围内。

## 3. 实施顺序与边界

### ME-1.6H-A：寄存请求号与提货显示文案

- **范围**：`QuantityBenefitPanel` 的寄存 `reqId` 生命周期；提货相关列表、流水和可见字典的业务文案。
- **实现**：将寄存首次提交时创建并缓存的 `REQ${Date.now()}` 发送给既有寄存接口；在成功/取消/关闭时清除。
  只在展示层将 `MEMBER_PICKUP` 映射为“会员提货”。
- **不得改变**：普通 POS 的 `usePosStore` 所有权；提货 `MP*` 业务单号；实体库存只在提货扣减；历史数据。
- **验收**：寄存请求 ID 的样式为 `REQ` 加 13 位毫秒值；失败重试不产生第二笔订单；提货的业务单、权益及库存
  流水仍可追溯，界面不向操作员暴露 `MEMBER_PICKUP` 技术码。

### ME-1.6H-B：寄存普通订单小票

- **范围**：QUANTITY 寄存成功后的前端触发与既有订单小票 API 复用。
- **实现**：从既有寄存成功响应取得订单号后，调用
  `/oms-order/hardware/checkout-receipt`；遵循普通 Checkout 的非阻塞错误提示方式。
- **不得改变**：订单写入事务、付款校验、打印配置、钱箱规则或小票模板。
- **验收**：成功寄存触发一次普通订单小票；打印失败仍显示寄存成功且可提示操作员；重复请求命中幂等结果时不因
  页面重试自动重复打印。

### ME-1.6H-C：会员提货单与打印

- **范围**：TRADE/打印边界中的提货只读快照、受保护打印端点、模板/硬件调用，以及提货成功后触发。
- **实现**：以既有 `OmsMemberQuantityPickup` 及其明细为权威来源，新增最窄的“会员提货单”读取/打印能力。
  如需要跨 Feature 的会员/商品显示数据，只能通过 `money-app-api` 的 Entity-free 快照契约取得；不得直接依赖
  UMS/GMS Entity、Mapper 或实现类。
- **权限**：提货打印接口至少要求既有 `memberBenefit:operate`；不得借此扩大普通订单打印权限。
- **不得改变**：提货的原子事务、库存命令、权益扣减、订单模型、收入/支付报表、普通订单小票。
- **验收**：成功提货仅触发一次标题正确的提货单；小票数据对应实际提货明细；无权访问被拒绝；打印异常不回滚
  提货；普通订单打印回归不变。

### ME-1.6H-D：最终验证与收口

- **自动验证**：覆盖 H-A 的 reqId 幂等、显示映射，H-B 的打印触发边界，H-C 的权限、数据归属和打印失败不回滚；
  运行相关 Maven 回归、完整 `mvn -q test`、`mvn -q package -DskipTests`、Node 20 `npm run build`、两项架构扫描
  与 `git diff --check`。
- **Windows Electron 验收**：验证 1280×800 POS、普通购物车隔离、寄存试算/支付/下单/打印、提货/库存扣减/提货单
  打印、失败提示和重试不重复打印，以及既有 AMOUNT/TARGET 成功与拒绝路径。
- **完成条件**：每项验证有实际结果；本合同和 handoff 记录事实；每个完成切片由 Codex 提交、推送、fetch，且
  `dev...origin/dev` 无 ahead/behind。Windows 验收未完成时不得宣称 ME-1.6 最终关闭。

## 4. 不可变架构与数据边界

- QUANTITY 寄存继续通过既有普通订单结算路径确认收入，但不扣实体库存；提货继续由
  `DeferredQuantityPickupService` 处理并在提货时扣库存。
- 打印是成功交易后的副作用，不获得订单、库存或会员事务所有权，也不能改变其回滚边界。
- 任何新增跨 Feature 数据合作必须使用 `money-app-api` 的 Entity-free contract；禁止 Entity、Mapper 或
  implementation-class 依赖。
- 不新增通用“权益订单”或通用“权益小票”实体；本合同只有普通订单小票复用和 QUANTITY 提货单。

## 5. 非目标

- 不改变 AMOUNT/TARGET 流程、退款、会员价格、优惠、支付分摊或普通 Checkout 请求号行为。
- 不修改历史 `MEMBER_PICKUP` 数据或数据库枚举值，不迁移既有提货单号。
- 不新增补打、批量打印、电子小票、退款小票或其他权益类型的小票。
