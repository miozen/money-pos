# MoneyPOS ME-1.6K：可读业务单据编号统一决策合同

> 状态：**已确认，授权实施**；确认日期：2026-10-12；修订日期：2026-10-12；适用分支：`dev`。

## 1. 范围与目标

本合同统一**新生成**的普通销售、商品寄存、权益提货和非商品权益凭证的业务单据号，使其具有可读的
“业务类型 + 日期时间 + 当日序号”形式。历史单据保持原值，不回写、不改号。

| 业务单据 | 前缀 | 新格式示例 |
| --- | --- | --- |
| 普通销售订单 | `REQ` | `REQ202610121108420004` |
| 商品寄存订单 | `QDP` | `QDP202610121108420004` |
| 数量权益提货单 | `MP` | `MP202610121108420004` |
| 金额权益提货单 | `MAP` | `MAP202610121108420004` |
| 金额权益凭证（含提货补差/退款） | `MAR` / `MARF` | `MAR202610121108420004` |
| TARGET 补差/豁免凭证 | `MTR` | `MTR202610121108420004` |

格式为 `<前缀><yyyyMMddHHmmss><四位当日序号>`。日期时间采用服务器本地业务时钟；序号在同一
租户、业务前缀和自然日内独立递增、每天从 `0001` 开始。业务前缀保留原有语义，序号不能由前端生成或以 Snowflake 长数字替代。
四位序号每个租户、每种单据每天最多 `9999` 张；达到上限必须明确报错，不得回绕或复用。

本合同只覆盖上表的 ME-1.6 交易单据。充值、库存、采购等其他领域单据不在本次范围，不能借此改号。

## 2. 幂等性与历史兼容

1. 请求号（`reqId` / `request_no`）仍是客户端重试的幂等键，且不再承担普通订单的展示业务单号职责。
2. `oms_order` 为新单据增加独立 `request_no`，新建唯一索引；普通 Checkout 先按该字段查重。历史订单
   `request_no` 保持空值，旧 `order_no` 不变，原有详情、支付、退款、打印、统计继续按 `order_no` 关联。
3. QDP 是写入 `oms_order` 的寄存订单：其请求号仍是 `QDPyyyyMMddHHmmssSSS`，新业务 `order_no` 由服务端生成
   为上表 `QDP...` 格式。
4. MP/MAP/MAR/MARF/MTR 原有独立 `request_no` 的幂等语义不变；只替换其新建业务单据号生成器。
5. 不按编号前缀推断单据类型；已有详情路由、账本来源、退款和打印使用已存类型/表关系。

## 3. 生成器、事务与并发

1. 新增 TRADE 所有的单据号序列持久化表，键为 `tenant_id + document_prefix + business_date`，以单条原子递增 SQL 取得当日序号。
2. 生成器必须在创建相应业务单据的既有 Spring 事务内调用；后续业务失败时序号可有空洞，但不得回退、复用或造成冲突。
3. 编号字段最大长度不超过现有 `varchar(32|64)`；不新增跨 Feature Entity/Mapper 依赖。
4. 不修改支付、库存、权益账本、退款金额、权限、请求路由或打印触发条件。

## 4. 验收与不变项

- 同秒连续生成能得到不同、可排序且同日递增的四位序号；跨租户、跨前缀独立计数，跨日从 `0001` 重新开始。
- 普通订单和 QDP 使用独立请求号防重放；重复请求返回原业务订单，不新增单据。
- MP/MAP/MAR/MTR 仍以原请求号幂等；历史 Snowflake 编号可正常查询、详情、退款/打印。
- 不迁移或重写历史单据编号。
