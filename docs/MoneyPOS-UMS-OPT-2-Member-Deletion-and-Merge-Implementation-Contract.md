# UMS-OPT-2：会员误建删除与重复档案合并实施契约

> 状态：**已确认，按 UMS-MERGE-0～4 渐进实施**；确认日期：2026-10-16；适用分支：`dev`。

## 1. 问题与目标

现有 `DELETE /ums/member` 会对选中的会员直接设置 `deleted=true`，并将 `balance`、`coupon` 清零。
它不检查充值、订单、券钱包或会员权益。该行为不适合作为重复会员档案合并手段，也会使误操作丢失当前可用资产。

本契约将两种业务动作分开：

1. **删除误建空档案**：仅允许删除没有任何业务痕迹的会员；
2. **合并重复档案**：管理员人工确认来源会员与保留会员后，受控地转移第一版允许转移的资产，并保留全部历史归属与审计。

会员姓名不是身份唯一键；不得按同名、手机号或其他字段自动合并。

## 2. 已冻结业务规则

1. 同名会员可以正常共存。合并只能由操作员手工选择来源和目标，系统不提供自动候选或自动合并。
2. 删除继续复用既有 `DELETE /ums/member` 与 `umsMember:del`；它只用于误建的空档案。
3. 有业务数据的会员不得删除。重复会员须走专用合并动作。
4. 合并仅限同一租户、两个有效且未合并会员；来源与目标不得相同。
5. 合并后来源会员不可再交易、充值、编辑、删除或再次合并，并能追溯其保留目标。
6. 历史订单、支付、退款、充值凭证、历史资产流水、已使用/失效券及权益流水保留原 `member_id`，不回写。
7. 第一版合并仅转移来源会员的当前余额与 `UNUSED` 状态会员券。余额转移须在来源和目标各留一笔关联同一合并单号的资产流水；券保留自身实体与原发券/订单关联，仅变更当前会员归属。
8. 第一版不转移会员档案资料、品牌等级、数量权益、金额权益或 TARGET 计划。目标会员档案资料和品牌等级始终为准。
9. 来源会员存在任何数量权益、金额权益或 TARGET 计划（含已完成、已取消、复核状态）的，第一版拒绝合并；不得猜测或重写已冻结权益账本的历史归属。
10. 第一版合并不可自动撤销。原始数据和合并审计保留；误操作后的反向处置必须由后续独立业务契约定义。
11. 日常内部操作不增加菜单、角色或权限码：预览/执行合并复用 `umsMember:edit`；删除仍使用 `umsMember:del`。

## 3. 删除准入矩阵

删除前必须确认该会员同时满足：

| 检查项 | 允许删除条件 | 所有者/判定方式 |
| --- | --- | --- |
| 当前余额与券额度 | 均为零 | UMS `ums_member` |
| 充值与资产流水 | 不存在 | UMS 充值单、`ums_member_log` |
| 会员券钱包 | 不存在任意状态券 | UMS `pos_member_coupon` |
| 订单/支付/退款 | 不存在 | TRADE 以 `money-app-api` Entity-free 存在性查询提供 |
| 品牌等级 | 不存在 | UMS `ums_member_brand_level` |
| 数量/金额权益、TARGET 计划 | 均不存在 | UMS 权益账本 |
| 已合并标记 | 不存在 | UMS 合并审计/来源关联 |

批量删除采用全有或全无语义：任一会员不满足条件，整个请求失败，且不得清零余额或券。

## 4. 合并准入与结果矩阵

| 来源会员状态 | 删除 | 合并 | 第一版处理 |
| --- | ---: | ---: | --- |
| 无任何业务痕迹 | 允许 | 允许 | 管理员选择删除或合并 |
| 有历史订单/充值，但无当前资产、无权益 | 拒绝 | 允许 | 历史保留在来源；来源标记已合并 |
| 有余额 | 拒绝 | 允许 | 同一 UMS 事务内转入目标并写双向资产流水 |
| 有未使用券 | 拒绝 | 允许 | 将 `UNUSED` 券归属转到目标，保留券记录 |
| 有数量/金额权益 | 拒绝 | 拒绝 | 先人工处理或后续单独定义转移规则 |
| 有 TARGET 计划或退款复核关联 | 拒绝 | 拒绝 | 不改变现有履约、退款和复核规则 |
| 已删除/已合并 | 拒绝 | 拒绝 | 仅允许审计查询 |

## 5. 实施切片

### UMS-MERGE-0：契约与事实盘点（本切片）

- 固化本契约、准入矩阵与验收边界；
- 盘点会员、资产、券、权益与 TRADE 订单引用；
- 不修改业务代码、路由、数据库或前端。

### UMS-MERGE-1：安全删除守卫

- 保留既有删除路由、请求/响应与权限；
- 在 UMS 服务中实施删除准入矩阵；TRADE 订单存在性以新建的 Entity-free 窄查询契约提供；
- 删除批次在一个事务中预检并全有或全无执行；
- 不再执行余额/券清零或 `[注销]` 改名。

### UMS-MERGE-2：合并预览与审计模型

- Flyway 新增 UMS 自有合并审计表及来源到目标的可追溯关系；不改历史表记录；
- 新增受 `umsMember:edit` 保护的合并预览和历史查询接口；
- 预览返回双方资料摘要、余额、未使用券、历史业务计数、权益阻断项与可合并结论。

### UMS-MERGE-3：受控合并命令

- 新增受 `umsMember:edit` 保护的合并执行接口，含请求号、来源、目标与必填原因；
- 在单一 UMS 事务内锁定会员、复检状态、转移余额/未使用券、写审计、标记来源已合并；
- 合并请求必须可幂等；同一来源不得产生两次成功合并；
- 针对合并与充值、扣款、退款的并发，补充活动会员守卫或等价原子条件，但不改变现有金额公式和 TRADE 事务所有权。

### UMS-MERGE-4：管理端最小交互

- 删除入口显示“仅无业务数据的误建档案可删除”；
- 增加人工选择“来源 → 保留”方向的合并流程，展示预览、阻断原因、资产转移摘要和二次确认；
- 合并原因必填；成功后刷新目标档案，来源显示“已合并至目标会员”；
- 不实现自动匹配、自动合并或撤销合并。

## 6. 架构与兼容边界

- UMS 继续拥有会员、余额、券、充值、权益和合并审计写入；TRADE 继续拥有订单、支付和退款。
- 新增跨 Feature 协作只能位于 `money-app-api` 的 Entity-free 查询契约中；UMS 不得引用 TRADE Entity、Mapper 或实现类。
- 不修改已发布订单/支付/退款/充值路由、响应、金额公式、存量数据或已验收的权益履约逻辑。
- 所有余额、券归属、审计和来源状态更新必须同事务提交；失败时全部回滚。

## 7. 验收与验证

每个实施切片至少覆盖受影响的集成回归，以及 `mvn -q package -DskipTests`、两项架构扫描和 `git diff --check`；完成切片时按仓库隔离数据库协议运行全量 Maven 回归并更新 Handoff。

关键验收：

1. 空会员可删除；任一业务痕迹阻止删除，批量删除不产生部分成功；
2. 合并绝不自动依据姓名判断；跨租户、同一 ID、无效或已合并来源均失败；
3. 合并前后余额总额守恒，未使用券数量守恒；
4. 历史订单、充值、支付、退款、资产流水与权益流水的 `member_id` 不被回写；
5. 重复请求、并发合并及合并期间资产操作不产生重复转移或半完成状态；
6. 不出现跨 Feature Entity/Mapper/实现类依赖，也不改变既有权限模型。
