# MoneyPOS UX-3：零库存商品提示与拦截设计

> 初始审查日期：2026-09-23；源码基线：`dev`。不涉及数据库或库存事务改造。

## UX-3.1 已确认的最小实施范围

根据收银台实际使用反馈，本轮不把库存异常前移为购物车或收款按钮的前端硬拦截。保留现有流程：商品可加入购物车；打开结算台、正式收款时仍由服务端库存校验拒绝不足库存。

本轮仅实施以下两项：

- 购物车对 `qty > stock` 的商品显示浅红行背景、警示图标，以及“库存为 0，已选 N”或“库存不足：现有 X，已选 Y”的常驻文字。
- 异常行显示“补货”按钮，复用 POS 现有入库弹窗并自动带入该商品；入库成功后重新读取购物车商品库存并触发现有试算，库存足够时标记自然消失。

不实施本文件原先建议的聚合提示、顶部错误静默、库存问题状态模型、收款按钮禁用或结算窗问题清单。这些可在实际使用后另行评估，不能改变本轮“快速发现、快速补货、后端结算兜底”的边界。

## 结论

保留当前产品规则：**零库存或数量超过库存的商品可以进入购物车，但不能收款结算。** 这对门店补货、换货和继续扫描场景更灵活；优化目标是让收银员在加入、编辑数量和点击收款前，都能一眼看到原因并立刻去补货，而不是等待顶部错误提示自动消失。

后端库存扣减不应移到前端，也不应因为 UX-3 放松。前端提示只是一层可用性反馈；试算和最终结算仍是库存正确性的两道服务端防线。

## 当前链路审查

| 环节 | 当前行为 | 问题 |
| --- | --- | --- |
| 扫码、搜索选择、极速建档 | 都直接调用 `addToCart()`；`stock=0` 仍能进入购物车。 | 符合保留购物车的规则，但没有明确提示。 |
| 搜索建议 | `BottomConsole.vue` 以红色“存: 0”显示零库存。 | 颜色/小标签存在，但选中后缺少行动提示。 |
| 购物车 | 仅当 `qty > stock` 时把库存数字标红；数量控件上限固定 `9999`。 | 无“缺货”状态、无超出数量说明、无收款阻断说明；零库存非常容易被忽略。 |
| 前端试算 | `runTrial()` 防抖 300ms 调用 `/pos/trial`。服务端库存不足会抛异常；前端只记录 console。 | Axios 全局拦截器会将异常变成顶部 `ElMessage`，可能遮挡 POS 顶部操作；试算状态没有可持久展示的库存问题模型。 |
| 正式收款 | `CheckoutModal` 仅根据试算中、实付不足、会员券判断是否禁用收款。 | 本地已知库存不足时，收款按钮仍可能可点，直到服务端拒绝。 |
| 服务端试算 | `PosCalculationEngine` 查询当前库存，`quantity > stock` 时抛 `STOCK_NOT_ENOUGH`。 | 正确的读时校验。 |
| 正式结算 | 结算事务内再次试算；随后 GMS 用 `UPDATE ... WHERE stock >= qty` 原子扣减，失败则回滚。套餐也扣减套餐配额和子商品库存。 | 正确的最终并发防超卖边界，必须保留。 |

`stock=null` 在服务端试算中按 `0` 处理；前端 UX-3 也必须统一按 `0` 显示和判断，不能把它误显示为“未知但可售”。套餐的实际可售性还依赖子商品配额，前端不能声称本地 `stock` 是最终保证。

## 目标状态模型

在 `usePosStore` 建立仅供界面使用的派生状态，不写库：

| 状态 | 条件 | 行为 |
| --- | --- | --- |
| 可售 | `qty <= max(stock, 0)`，且没有服务端最新失败信息 | 正常显示、可进入收款。 |
| 缺货 | `stock <= 0` 且购物车数量大于零 | 商品保留在购物车；红色“缺货”状态；阻止收款。 |
| 数量超出 | `qty > stock > 0` | 显示“库存 X，已选 Y”；阻止收款。 |
| 服务端库存变化/套餐不足 | 试算或结算返回库存不足 | 显示服务端给出的原因；阻止或保持收款失败，提示刷新/补货。 |

状态必须根据购物车每次增删、扫码、搜索选择、数字输入、键盘加减、挂单取回而实时重算。库存快照仅用来提供即时反馈；它不会替代服务端判断。

## 推荐交互

1. **加入时保留商品。** 扫到/选到零库存商品后仍加入购物车，激活该行；不弹阻塞确认框。
2. **购物车行内常驻状态。** 库存列从单一红数字升级为可读标签：`缺货` 或 `库存 3，已选 5`；整行浅红高亮，数量控件/商品名附近也有错误图标。正常库存继续显示数量。
3. **收款区聚合提示。** POS 底部或购物车底部显示常驻、可关闭但不遮挡导航的提示，例如“2 项库存问题，处理后才能收款”；点击可定位第一条问题行。不要使用顶部全局 `ElMessage` 作为库存问题的主要反馈。
4. **收款前硬性前端阻止。** `CheckoutModal` 根据 `hasStockIssue` 禁用“确认收款”，并在弹窗内显示同一份问题清单；收银员无需输入支付再等待服务端报错。
5. **补货入口。** 聚合提示和结算弹窗提供“去补货”动作，先复用现有 `RestockModal`。第一版只打开补货面板，不自动入库、不改变购物车、不假设补货成功；补货后收银员可重新搜索/刷新商品，再继续收款。
6. **后端拒绝的可读反馈。** 将 POS 试算请求的库存错误从通用全局顶部 toast 中隔离出来，转为本地库存问题状态；非库存错误仍沿用现有全局错误机制。正式结算遇到并发抢购/套餐子品不足时，结算弹窗保留并显示服务端原因，购物车不清空。

## 最小实现范围

前端为主，后端只在需要把试算失败结构化传回前端时做最小契约补充：

- `money-pos-web/src/views/pos/hooks/usePosStore.js`：派生 `stockIssues`、`hasStockIssue`，在本地库存不足时避免重复触发会产生顶部提示的无效试算；清除过期试算结果。
- `CartTable.vue`：行内缺货/超量标签、行高亮和聚焦定位。
- `BottomConsole.vue`：聚合库存状态和“去补货”事件入口。
- `CheckoutModal.vue`：将库存问题纳入提交禁用条件并展示问题清单。
- `pos/index.vue`：连接“去补货”到现有补货弹窗；不改变订单逻辑。
- `axios.js`（仅必要时）：为特定 POS 试算请求提供“由调用方展示错误”的静默选项；不得静默真实网络、401/403 或其他业务错误。
- 后端（仅必要时）：库存不足响应包含稳定的商品 ID、请求数量、当前库存/套餐原因，以便前端把问题精确映射到购物车行；正式结算与原子扣减逻辑保持不变。

不做数据库/Flyway、不新增库存预占、不自动挂单、不自动补货、不允许负库存，也不把商品搜索接口按库存过滤掉。

## 套餐与并发边界

- 普通商品可以用搜索快照给即时状态；套餐本地配额并不代表子商品都有库存。
- 所有套餐可售、并发抢购、后台同时出入库和另一台收银机结算，最终仍由试算/结算与 GMS 原子扣减裁定。
- 若前端显示可售而结算时库存发生变化，必须保留购物车、显示准确后端原因并允许收银员修改数量、补货或挂单后重试；绝不生成订单或扣减会员资产。

## 验收矩阵

| 场景 | 预期 |
| --- | --- |
| 扫描零库存普通商品 | 进入购物车，当前行显示“缺货”，收款不可用；顶部菜单仍可操作。 |
| 搜索选择零库存商品 | 搜索结果和购物车均清晰标识，行为与扫码一致。 |
| 数量从可售改为超库存 | 立即显示“库存 X，已选 Y”，收款禁用。 |
| 将数量降回可售 | 行内和聚合问题消失；试算恢复，满足其他付款条件后可收款。 |
| 挂单取回含缺货商品 | 重新按当前/服务端库存检查，不沿用旧的“可售”假设。 |
| 套餐配额或子品不足 | 显示服务端可读原因，订单、支付和库存均不落库。 |
| 并发库存变化 | 即时提示可能滞后，但正式结算必须原子拒绝并保留购物车。 |
| 补货后 | 商品刷新后可重新试算/收款；第一版不承诺自动更新购物车库存。 |
| 非库存试算错误、401、网络错误 | 继续使用现有错误与锁屏机制，不被库存静默规则吞掉。 |

## 建议切片

先实施 UX-3.1：本地库存问题模型、行内/聚合反馈、结算按钮禁用与非阻塞“去补货”入口。随后按实际试算错误表现决定 UX-3.2 是否需要后端结构化库存失败契约。这样可先消除最常见的零库存误操作和顶部遮挡问题，同时不扩大库存领域改造。
